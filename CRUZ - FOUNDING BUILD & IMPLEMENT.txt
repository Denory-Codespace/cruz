# 2. PRODUCT VISION

Cruz should eventually become a complete mobility platform.

However:

## DO NOT BUILD EVERYTHING AT ONCE.

Our first objective is a **Minimum Viable Ride-Hailing Platform (MVP)**.

The MVP must prove this complete loop:

```text
Passenger
    ↓
Requests ride
    ↓
Cruz finds available driver
    ↓
Driver receives request
    ↓
Driver accepts
    ↓
Passenger sees driver
    ↓
Driver travels to passenger
    ↓
Trip starts
    ↓
Trip happens
    ↓
Trip ends
    ↓
Fare calculated
    ↓
Payment recorded
    ↓
Driver earnings recorded
    ↓
Platform commission recorded
    ↓
Passenger rates driver
```

If this loop works reliably, Cruz has a legitimate technological foundation.

Do not distract the project with secondary features before this core journey works.

# 3. DEVELOPMENT PHILOSOPHY

Follow these principles throughout the project:

### 3.1 Build for reality

Do not create fake buttons, fake APIs, fake databases, fake authentication, or simulated functionality unless a feature is explicitly marked as a prototype.

### 3.2 Start simple

Do not introduce microservices, Kubernetes, complex cloud architecture, event buses, service meshes, or expensive infrastructure prematurely.

### 3.3 Design for future scale

Simple does NOT mean poorly designed.

The architecture must allow Cruz to evolve later.

### 3.4 Own our data

Cruz's business logic, database schema, domain model, and source code must remain portable.

Avoid unnecessary vendor lock-in.

### 3.5 Security first

Never compromise authentication, authorization, financial integrity, privacy, or user data simply to move faster.

### 3.6 Free-first

Use free tiers and open-source technologies wherever practical.

### 3.7 Documentation-first

Every important architectural decision must be documented.

### 3.8 Test critical functionality

Trips, payments, driver assignment, authentication, authorization, wallet transactions, and state transitions require automated tests.

### 3.9 AI must not freestyle

Do not invent requirements.

If a requirement is unclear:

1. Inspect existing documentation.
2. Infer only where safe.
3. Document the assumption.
4. Ask the human when the decision materially affects architecture, cost, security, legal compliance, or product behavior.

# 16. LOCATION/GPS ARCHITECTURE

Location is a core Cruz feature.

The system must distinguish between:

### Driver current location

Where the driver currently is.

### Trip location history

Location information associated with a particular trip.

### Driver availability

Whether the driver is currently available for matching.

Do not permanently write every GPS update directly to the primary PostgreSQL database at high frequency.

Design an efficient approach.

Initially a reasonable prototype approach may use:

```text
Driver
   ↓
Location update
   ↓
Realtime/temporary state
   ↓
Matching engine
```

with selected trip/location information persisted for operational/safety purposes.

Document the strategy.

# 21. DRIVER MATCHING

The first matching engine should be simple and reliable.

Initial logic:

```text
Passenger requests ride
        ↓
Find eligible drivers
        ↓
Filter:
  - online
  - available
  - approved
  - correct vehicle category
  - not already on a trip
        ↓
Rank candidates
        ↓
Estimate distance/ETA
        ↓
Offer ride
        ↓
Driver accepts
        ↓
Lock/assign trip
```

Avoid building an overly sophisticated AI matching system initially.

The first algorithm should prioritize:

1. Availability
2. Eligibility
3. ETA/distance
4. Fairness/dispatch rules
5. Reliability

Document the algorithm in:

`/docs/architecture/dispatch.md`

# 22. CONCURRENCY

Ride assignment is a concurrency-sensitive operation.

Consider:

```text
Passenger requests ride.

Driver A sees request.
Driver B sees request.

Both accept almost simultaneously.
```

The system must guarantee that the trip is assigned correctly.

Use database transactions/locking/idempotency where appropriate.

Write automated tests for concurrent acceptance scenarios.

This is a high-priority engineering requirement.

1. Do we need it?
2. Is there already a native/framework solution?
3. Is it maintained?
4. Is its license appropriate?
5. Does it introduce security risk?
6. Does it create vendor lock-in?
7. Is the bundle/runtime impact acceptable?

Prefer mature, well-supported libraries.
